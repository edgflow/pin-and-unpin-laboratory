# Lesson 6 · `Pin<Box<T>>` and `BoxFuture`

Part 2, Understand Pin. Code: `src/lesson06_pin_box.rs`, `src/crank.rs`, tests in
`src/lesson06_pin_box/tests.rs`, and `examples/boxed_future.rs`.

```console
$ cargo run -- 6
$ cargo run --example boxed_future
$ cargo test lesson06
$ cargo +nightly miri test lesson06
```

Up to here the pinned thing was our `Frame`. From here on it is the thing that gets pinned most often in real
Rust: a **future**. This lesson treats a future as a black box that can be asked "are you done?". Lesson 7
opens the box. To run futures before then, `src/crank.rs` has a deliberately crude helper, `turn`, which asks
in a loop and counts how many times it had to ask.

## A · The problem

A connection can do several things: read a frame, send a ping, close. Each is an `async fn`. We want to keep
pending operations in one list and work through them.

## B · The naive implementations

**First try: put them in a `Vec`.** (`invalid/lesson06_two_types_one_vec.rs`, not part of the build.)

```rust
let jobs = vec![ping(), close()];
```

```text
error[E0308]: mismatched types
15 |     let jobs = vec![ping(), close()];
   |                             ^^^^^^^ expected future, found a different future
   = note: distinct uses of `impl Trait` result in different opaque types
```

Both functions are `async fn … -> String`. Their futures are still two different types, each generated by the
compiler for that one function, with no name we can write. Block 1 of the run below measures it: 96 bytes,
24 bytes, 1 byte.

**Second try: erase the type with a trait object.** `Box<dyn Future<Output = String>>` is one type, whatever
is inside. Storing works. Running does not (`invalid/lesson06_box_without_pin.rs`):

```rust
let job: Box<dyn Future<Output = String>> = Box::new(ping());
job.await
```

```text
error[E0277]: `dyn Future<Output = String>` cannot be unpinned
16 |     job.await
   |         ^^^^^ the trait `Unpin` is not implemented for `dyn Future<Output = String>`
   = note: consider using the `pin!` macro
           consider using `Box::pin` if you need to access the pinned value outside of the current scope
   = note: required for `Box<dyn Future<Output = String>>` to implement `Future`
```

Read the last note: *required for `Box<dyn Future>` to implement `Future`*. A plain box of a future is only
itself a future when the thing inside is `Unpin`. Lesson 4 gave us the vocabulary for why.

## The working example

```rust
pub type BoxFuture<'a, T> = Pin<Box<dyn Future<Output = T> + Send + 'a>>;

let mut jobs: Vec<BoxFuture<'static, String>> =
    vec![Box::pin(read), Box::pin(ping_once), Box::pin(close_now)];
```

One real run:

```text
1. three futures, three types
  read_frame     96 bytes  !Unpin
  ping           24 bytes  !Unpin
  close           1 bytes  !Unpin

2. the same three as BoxFuture<String>
  each is 16 bytes
  and is Unpin: true

3. reversed the list and grew it
  every future stayed where it was: true

4. run them, last to first
  "closed" after 1 poll(s)
  "pong" after 2 poll(s)
  "frame 7, first byte 'G'" after 3 poll(s)

5. a BoxFuture that borrows: length 11

6. countdown(3) = 3, after 4 polls

7. operations as trait objects
  read   "frame 9, first byte 'G'"
  ping   "pong"
  close  "closed"
```

## C · What happens in memory

Illustrative addresses.

Before: three futures of three types and three sizes. They cannot share a `Vec`.

```text
 read_frame's future        ping's future        close's future
 ┌───────────────────┐      ┌───────────┐        ┌─┐
 │     96 bytes      │      │  24 bytes │        │1│
 └───────────────────┘      └───────────┘        └─┘
```

After `Box::pin`, coerced to `BoxFuture<String>`: every element of the `Vec` is the same 16 bytes.

```text
 Vec<BoxFuture<String>>                    HEAP
 ┌──────────────┬──────────────┐
 │ data  0x6000 │ vtable 0x1000├─────────▶ 0x6000 ┌───────────────────┐  read_frame's future
 ├──────────────┼──────────────┤                  │ 96 bytes, PINNED  │
 │ data  0x6100 │ vtable 0x1040├─────┐            └───────────────────┘
 ├──────────────┼──────────────┤     └───▶ 0x6100 ┌───────────┐          ping's future
 │ data  0x6200 │ vtable 0x1080├──┐               │ 24 bytes  │
 └──────────────┴──────────────┘  │               └───────────┘
   16 bytes each: a "fat" pointer └──────▶ 0x6200 ┌─┐                    close's future
                                                  │1│
                                                  └─┘

 PROGRAM CODE (read-only)
 0x1000  vtable for read_frame's future:  size, alignment, drop, poll ──▶ read_frame's code
 0x1040  vtable for ping's future:        size, alignment, drop, poll ──▶ ping's code
 0x1080  vtable for close's future:       size, alignment, drop, poll ──▶ close's code
```

Four words from the lesson's title are all in that picture:

- **Heap allocation.** Each future is in its own block. The `Vec` holds only pointers.
- **Type erasure.** The element type no longer says which future it is. The *size* is erased too: that is why
  a 96-byte and a 1-byte future fit the same slot.
- **Trait object.** The second half of each fat pointer is a vtable: a table the compiler builds per concrete
  type, holding what the erased type can no longer tell us (its size, how to drop it, where its `poll` is).
- **Dynamic dispatch.** Block 4 runs one loop over the list. Each call to `poll` goes through the vtable to a
  different function. Which one is decided at run time.

And block 3: reversing the `Vec` and growing it moved the 16-byte pointers around. The futures at `0x6000`,
`0x6100` and `0x6200` did not move. Lesson 1's challenge, lesson 3's diagram, the same fact.

## D · The compiler's perspective

**Why `Box<dyn Future>` is not enough.** `Future::poll` takes `self: Pin<&mut Self>` (lesson 7 is about why).
To call it on the contents of a plain box we would need `Pin<&mut dyn Future>`. The safe way to make a `Pin`
from a `&mut` is `Pin::new`, and that requires the target to be `Unpin` (lesson 4):

```text
error[E0277]: `dyn Future<Output = String>` cannot be unpinned
21 |     let _pinned = Pin::new(&mut *job);
note: required by a bound in `Pin::<Ptr>::new`
```

`dyn Future` is not `Unpin`, and that is not an accident. Once the type is erased, the compiler has to assume
the worst case: the future inside may be address-sensitive. Block 1 shows that the common case *is* the worst
case: all three `async fn` futures are `!Unpin`.

**What `Pin<Box<dyn Future>>` adds is a promise, not a mechanism.** The two types are the same 16 bytes
pointing at the same allocation. The difference is what the type says, and so which methods exist:

| | `Box<dyn Future>` | `Pin<Box<dyn Future>>` |
|---|---|---|
| Is the future at a stable address? | yes, in practice | yes, **by contract** |
| Can safe code get `&mut` to the future and move it? | yes, for a sized `T` (`mem::swap(&mut *a, &mut *b)`) | no |
| Can it be polled or awaited? | only if the future is `Unpin` | always |
| Is the pointer itself `Unpin`, movable, storable? | yes | yes |

How does `Pin<Box<dyn Future>>` get to be a future? Through this implementation in the standard library:
*`Pin<P>` is a `Future` whenever `P` is a pointer with mutable access to a `Future`.* No `Unpin` needed on the
target, because the pin already carries the promise.

**Going from one to the other is one safe call.** `Box::pin(value)` allocates and pins in one step.
`Box::into_pin(boxed)` converts a box you already have. Both are safe for any type, and the reason is
ownership: a `Box` is the only owner of its contents, so once we wrap it in a `Pin` nobody is left who could
reach in and move them. (The challenge below measures that the allocation does not change.)

**The other two parts of the alias.**

- `+ Send` promises that the boxed future may be moved to another thread. A future that keeps an `Rc` alive
  across an `.await` cannot make that promise (`invalid/lesson06_not_send.rs`):

  ```text
  error: future cannot be sent between threads safely
  note: captured value is not `Send`
  18 |         shared.len()
     |         ^^^^^^ has type `Rc<String>` which is not `Send`
     = note: required for the cast from `Pin<Box<{async block…}>>` to `Pin<Box<dyn Future<Output = usize> + Send>>`
  ```
  For single-threaded code, define the same alias without `Send`.
- `+ 'a` is the trait object's lifetime bound: the erased future may hold borrows that live at least as long
  as `'a`. `BoxFuture<'static, T>` holds no short borrows and can be stored anywhere. `length_later` in block 5
  returns `BoxFuture<'a, usize>` because its future keeps the `&'a str` it was given.

## E · The solution, and the three places you will really use it

```rust
pub type BoxFuture<'a, T> = Pin<Box<dyn Future<Output = T> + Send + 'a>>;
```

1. **A collection of different futures** (blocks 2 to 4, and `examples/boxed_future.rs`).
2. **Recursion** (block 6). An `async fn` that awaits itself would need a future that contains itself
   (`invalid/lesson06_recursion_without_a_box.rs`):

   ```text
   error[E0733]: recursion in an async fn requires boxing
      = note: a recursive `async fn` call must introduce indirection such as `Box::pin` to avoid an infinitely sized future
   ```
   `countdown` returns a `BoxFuture` instead, so each level is a pointer to the next one.
3. **Async methods on trait objects** (block 7). A `dyn Operation` cannot have a method returning "some
   future type", because every implementor's future is a different type and size. Returning `BoxFuture` gives
   them all one.

`examples/boxed_future.rs` puts the first use to work as a small job queue, polled round-robin:

```text
round 1: read      not yet
round 1: ping      not yet
round 1: close     done: "closed"
round 1: countdown not yet
round 2: read      not yet
round 2: ping      done: "pong"
round 2: countdown not yet
round 3: read      done: "frame 7, first byte 'G'"
round 3: countdown done: "2"
```

Every unfinished job is popped from the front and pushed to the back, round after round, while it is
half-way through its work. That is only correct because moving the queue entry moves the box and not the
future.

**The cost, so that you can choose.** One heap allocation per future, and an indirect call per poll. A
generic `F: Future` has neither. So: box when you need one type for many futures. Do not box by reflex.

## F · The important lines

```rust
vec![Box::pin(read), Box::pin(ping_once), Box::pin(close_now)];
```
Each `Box::pin(x)` is a `Pin<Box<ThatFuture>>`. The annotation on `jobs` makes the compiler coerce each one
to `Pin<Box<dyn Future<Output = String> + Send>>`. That coercion is where the type is erased and the vtable
pointer is attached.

```rust
let (answer, polls) = turn(job.as_mut());
```
`job` is `&mut BoxFuture<String>`. `as_mut()` reborrows it as `Pin<&mut dyn Future>`, which is exactly the
receiver `poll` wants. The box is not consumed and nothing moves.

```rust
pub fn length_later<'a>(text: &'a str) -> BoxFuture<'a, usize> {
    Box::pin(async move { pause().await; text.len() })
}
```
`async move` moves the reference `text` into the future. The returned type says so: `BoxFuture<'a, _>`.

```rust
1 + countdown(from - 1).await
```
Awaiting a `BoxFuture` works because `Pin<Box<dyn Future>>` is itself a future.

```rust
fn start(&self) -> BoxFuture<'_, String>;
```
`'_` ties the returned future to the borrow of `self`. An implementation may use `self` inside the future.

```rust
fn inside<T: ?Sized>(boxed: &Pin<Box<T>>) -> usize {
    std::ptr::from_ref::<T>(&**boxed).cast::<()>().addr()
}
```
The address of the future itself. `.cast::<()>()` drops the vtable half of the fat pointer and keeps the data
address.

## G · Experiment

1. **Change what a future holds.** In `read_frame`, change `[0u8; 64]` to `[0u8; 4096]`.
   *Prediction:* block 1 shows a much larger future for `read_frame`; block 2 still says 16 bytes. The buffer
   is used after an `.await`, so it has to be stored inside the future. Lesson 8 is about exactly that.
2. **Drop the `Send`.** Remove `+ Send` from the alias. *Prediction:* everything still compiles; the test
   that calls `must_be_send` does not. Then try the `Rc` example with your new alias: it compiles.
3. **Miri and a parked future.** While writing this lesson, a test took a shared reference to a future that
   was parked at an `.await` (to read its address) and then polled it again. All safe code. Miri's default
   aliasing model reported an error; its other model (`-Zmiri-tree-borrows`) did not. The test now reads the
   address before the first poll instead. Why a mere `&` to a parked future is a delicate thing is the subject
   of lesson 8.

## H · Common mistakes

- **"`Box<dyn Future>` and `Pin<Box<dyn Future>>` are the same."** The same bytes, different capabilities.
  Only the second can be polled when the future is not `Unpin`, which is nearly always.
- **"I need `unsafe` to pin a box."** `Box::pin` and `Box::into_pin` are safe.
- **"Every async function has to return `Pin<Box<…>>`."** No. An `async fn` returns its future directly, and
  `.await` pins it in place for you. Box only for the three uses in section E.
- **"`BoxFuture` is slow, avoid it."** One allocation and one indirect call per poll. Measure before caring.
- **Forgetting `Send`, or adding it blindly.** With `+ Send` you cannot hold an `Rc` or a `RefCell` borrow
  across an `.await`. Without it you cannot hand the future to a multi-threaded executor.
- **`BoxFuture<'static, T>` for a future that borrows.** The compiler will tell you the borrow does not live
  long enough. Give the alias the real lifetime.

## I · Challenge

You are handed a box that somebody else already made, without `Pin`:

```rust
let plain: Box<dyn Future<Output = String> + Send> = Box::new(ping());
```

Turn it into something `turn` can run, without `unsafe` and without allocating again. Before you run it:
is the future at a different address afterwards?

**Expected result:** `Box::into_pin(plain)`. Same allocation, same address, new type; then `turn` gives
`("pong", 2)`. The test `a_plain_box_becomes_a_pinned_box_with_into_pin` checks the address and the result.

The question for lesson 7: *every error in this lesson came from one signature,
`fn poll(self: Pin<&mut Self>, …)`. Why does `poll` insist on a pinned receiver, even for futures that have
nothing to protect?*
